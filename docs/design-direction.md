# Siftory 桌面端设计方案（Agent 产品形态）

2026-10-13 设计评审结论。状态：**方案已定，未实施**。本文档记录最终讨论方案与关键决策，作为后续分阶段实施的依据。

---

## 一、现状审查结论

当前 UI 是一个合格的 Chat App，但还不是一个 Agent 产品。

已做对、保持不变的部分：

- 居中单列对话、用户右对齐气泡 + 助手全文宽排版（Claude.ai 标准形态）
- 底部圆角卡片式 Composer、Enter 发送 / Stop、流式 Markdown（Streamdown + CJK）
- 鼠尾草绿灰调色板 + IBM Plex Sans，有辨识度，不是模板味
- Todo 面板、明暗主题、减少动效尊重

与 Codex / Claude 的差距：

| 级别 | 差距 | 主流参照 |
|---|---|---|
| P0 | Agent 活动呈现过弱：工具调用是一行小字，无输入/输出结构、无状态、无耗时、不可展开 | Codex 事件时间线 + 可展开工具卡；Claude Code 可折叠 tool blocks |
| P1 | 产物没有家：研究报告、文案、分镜、音视频没有承载面 | Claude Artifacts 右侧面板 |
| P1 | 人工控制缺位：产品原则 Human in Control 没有审批/确认组件 | Codex 内联审批卡 |
| P2 | 状态零散：连接/排队/错误/工具执行四种散落样式；模型是静态文字；无品牌化空状态 | status chip + 统一 system row |

**核心判断：现在把 Siftory 呈现为"一个会跑工具的聊天框"，而产品定义是"一个自主生产的编辑室"。缺的不是美化，是 Agent 工作流的骨架。**

注：原审查曾把"无会话列表"列为 P0，经讨论后推翻——见下节决策。

## 二、核心模型决策

### 1. 选题 = 会话（1:1）

- 左栏/首页的"选题"就是会话，只是用用户的语言命名。
- 一个选题从启动、研究、审批、修改到产出，全程住在同一条会话里。判断标准："这还是同一个故事吗？"是→继续当前会话；不是→开新选题。
- 后端容器只有会话（model/thinking/instructions、todos、历史都挂在 conversation 上），1:1 零协议发明。
- **Phase 3 例外**：主题订阅（如"每日 AI 简报"）是持续存在的容器，一个选题对应多个 run。届时列表变两级（选题 → runs），每个 run 打开仍是同一张工作台。等订阅功能真实存在时再建这层。

### 2. 不做会话列表

用户只关心最终产物。选题会话完成后，用户不需要再看会话内容，只保存每次的最终产物即可。会话数据仍存 SQLite（恢复与调试用），但 UI 不提供入口。

会话是车间，产物是商品。

### 3. 首页永远是产物库（信息总览）

- App 任何时候打开都落在首页，包括任务跑到一半时。不做"有进行中任务就跳进工作台"的条件路由。
- 首页三件套：发起框（常驻顶部，空库时兼作引导页）、进行中区块（卡片显示选题名、阶段条微缩版、当前活动、已耗时；中断/失败如实显示）、已完成网格。
- 点击卡片跳转：进行中 → 工作台；已完成 → 产物视图。
- **状态派生（最小化，Q6 决策）**：进行中 = 有活跃 run 的选题；已完成 = 无活跃 run。不做显式完成标记（无 complete 工具、无手动按钮）——状态纯派生自现有 busy 信号，零协议零存储。向已完成选题继续发消息即自动回到进行中。
- **收录规则**：进行中区块显示所有活会话；已完成区只保留登记过产物的选题，且**只显示最新若干条**（不分页、不做完整档案浏览，Q7 决策）；纯闲聊不进库（数据仍在 SQLite，UI 不收）。缓解：引导助手把值得留存的结论登记为产物。
- **失败/中断卡**点击落在工作台出错现场：错误信息、已登记的部分产物、两个动作（重试续跑 / 再创作新选题）。

### 4. 产物多态

"最终产物"不是以视频为主，可能只有文案、只有音频。规则一条：

**卡片主视觉 = 管道最末阶段的产物**（只跑了研究→报告是主角；只到叙事→文案是主角），其余产物以带类型标签的小行列出。阶段条语义随之修正：终点可变，到达站即完成，不预设每个选题必须走到 Produce。

产物渲染器一族三尺寸，一处类型适配逻辑多处复用：

| 尺寸 | 用于 |
|---|---|
| compact | 卡片小行、工作台产物台 |
| hero | 库卡片主视觉 |
| full | 选题页产物视图 |

| 产物类型 | hero 表现 | full 表现 |
|---|---|---|
| 视频 | 缩略帧 + 时长角标 | 播放器 |
| 音频 | 内联播放条 | 完整播放器 |
| 文案 / 研究报告 | 衬线前三行摘录 | 衬线全文阅读 |
| 图片组 | 封面 + 数量角标 | 画廊 |
| 分镜 | 场景缩略横条 | 逐场景视图 |

### 5. 选题页双态

- 进行中 → 工作台：对话 + Run 时间线 + 产物台。
- 已完成 → 产物视图：全部产物的阅读/播放页 + 「再创作」，不含会话。

### 6. 修改回路 = 再创作，不翻旧会话

做完要改（换竖屏、换配音、出续集）：从产物卡「再创作」出发，以该选题和已有产物为输入开新会话。产物成为会话之间的交接物。代价：不能回到旧会话接着聊。

新会话注入：原选题名 + 原产物索引（标题 + 相对路径列表），Agent 需要内容时用 read 自取；**不带旧会话历史**。

### 7. 单并发约束

后端单上下文，同时只允许一个选题在跑。运行中「+ 新选题」置灰并注明原因，不做排队管理。

### 关键组件

- **Run 时间线**：工具调用升级为结构化卡片（名称 + 关键参数一行 + 状态/耗时，点击展开输入输出），按助手回合分组。
- **阶段条**：发现→提炼→叙事→生成→制作，Run 进行中置顶。真序列，阶段标记是正当的，且是 Siftory 独有骨架，即辨识度本身。
- **Composer v2**：模型选择从 header 静态文字移入左下；新增「+ 来源」入口给 URL/RSS 资源池；header 只留品牌 + 状态 chip（连接/模型/排队数合一）。

（审批卡本期不做，见八·不做清单。）

## 四、视觉规范修订

保留现有调色板（是资产不是负债），只改用法：

| Token | 值 | 变化 |
|---|---|---|
| `--background` / `--foreground` | `#fafbfb` / `#242d2b` | 不变 |
| `--primary` / `--ring` | `#293c37` / `#286b68` | 不变，ring 仅用于焦点与阶段条当前态 |
| `--story-accent` | `#695078` | **启用**：阶段条、产物台、审批卡边框，成为叙事层专属色 |
| `--brand` | `#f4d56b` | 仅 logo 与空库引导，不进控件 |
| `--tool-running` | 新增 `#286b68` 12% 透明底 | 工具卡运行态 |

- **字体**：IBM Plex Sans（界面）+ IBM Plex Serif（仅产物台与故事正文，CJK 回退宋体系）。对话是工作，故事是作品——衬线是 "From Information to Story" 的视觉兑现，是全设计唯一大胆的一笔。
- **动效**：全 app 只保留一处非触发式动效——产物卡首次生成时从右缘滑入（300ms ease-out）。其余动效只响应用户操作。删除装饰性过渡（如 todo-subject 的颜色 transition）。
- **避开的模板味**：不加 eyebrow 标签、不加 01/02 装饰编号、链接不加「→」、不搞全场圆角卡片+灰阴影、不用等宽字体做数据标签。

## 五、产物存储方案

### 目录结构

```
<dataDir>/
  siftory.sqlite              # 会话 + 产物索引（元数据：类型/阶段/相对路径/大小/标题）
  auth.json  providers.json  agent.lock.sqlite
  workspace/                  # Agent 的文件世界（唯一文件树根）
    topics/
      固态电池解读-a1b2c3d4/    # ← 会话 cwd 设到这里
        artifacts/            # 登记的最终产物：产物库 UI 经索引只读这里
        sources/              # 原始资料（抓取的网页、RSS 条目）
        frames/               # 视频中间帧等大体积中间产物
        tmp/                  # 临时文件
```

决策要点：

1. **按选题分户**。现状所有会话共享扁平 `workspace/`（harness.ts），不同选题文件混放，必须改。
2. **topics 放在 workspace/ 下**而非与 workspace 平级：dataDir 根保持纯粹（只放应用状态），Agent 文件收敛一棵树；cwd 回落语义（"会话未设 cwd 时用 workspace/"）不破。
3. **artifacts/ 是唯一承重目录**：产物不是"Agent 写了就算"。产物协议提供 `register_artifact` 工具，Agent **显式调用**并给出 type/stage/title，host 校验文件在选题目录内 → 移入 `artifacts/` → 写 SQLite 索引；UI 只读索引。不做文件系统监听自动登记（分不清草稿与产物，也拿不到元数据）。sources/frames/tmp/ 是 Agent 的摆放约定，由 skill prompt 规定，不靠代码强制。
4. **cwd 设为选题目录根**。harness 已支持会话级 cwd 覆盖，改动小：建会话时分配目录并设置。
5. **产物索引存相对路径**（相对选题目录），将来整树迁移时索引不用改。
6. **文件不进 SQLite**（视频可能很大），DB 只存元数据。
7. **UI 不做删除**（Q7 决策）：选题数据只增不减；确需清理时用户在 Finder 手动删选题目录，存储层语义就是"删目录即删选题"。备份不变：停 Agent 拷 dataDir。
8. **存量不动**：workspace 根散文件与旧会话保持原样，不做迁移。

### 产物可见性：方案 A（应用管理）

产物放 Tauri 应用数据目录，用户在 Finder 中看不到。解法：每件产物带「在 Finder 中显示」「导出副本…」一等按钮。自媒体创作者拿 mp4 去发布一键可达，同时库完整性、删除、备份保持简单。

备选方案 B（`~/Movies/Siftory` 用户可见目录）待真实用户提出文件管理诉求再加，是加法不是推翻。

### 已知限制

中间产物（原始资料、中间帧）可能很占空间。先全保留，不做完成时自动清理；磁盘问题真实出现时再加"完成后清理 workspace"选项。**此项是欠账。**

## 六、workspace 的未来扩展

判断归属的规则一条：**谁写它、丢了能否重建、备份要不要带它**。

| 候选 | 谁写 | 可重建？ | 归属 | 时机 |
|---|---|---|---|---|
| `topics/` | Agent | 否 | workspace/ | 已定 |
| `skills/` | Agent 自固化工作法 | 否 | workspace/ | 重复模式第二次出现时 |
| `kb/` 知识库 | Agent | 否 | workspace/ | Phase 3 持续研究 |
| `assets/` 品牌资产 | 用户/应用 | 否 | workspace/ | 视频制作落地时 |
| 模型文件 | 应用下载 | **是** | Tauri cache 目录 | 本地 TTS 等落地时 |
| 内置 skills/prompts | 应用打包 | 是 | 应用包内 | 现状 |

四层位置模型：应用包内（只读随版本）/ dataDir 根（应用状态，备份带）/ workspace（Agent 文件世界，备份带）/ cache（可重建大文件，备份不带）。备份文档需注明 cache 目录可安全排除。

**不预建空目录**：skills/kb/assets 等对应功能落地时才建，命名届时由功能定义说了算。

### skills/kb 的写入风险

这两个目录 Agent 可写但意义不同：skills 是行为定义、kb 是长期积累。**审批机制本期整体不做**（Q3 决策），Agent 当前可自由改写自身工作法与知识库——这是有意的欠账，记入九·风险清单。Human in Control 暂由「停止按钮 + 对话纠偏 + 再创作」实现。

### pi-durable 能力验证结论（2026-10-13 已查证）

- **pi-durable 1.2.0 没有 skill 机制**：无 skill 概念、无加载路径、无目录约定。pi 生态的 skill 系统（~/.agents/skills、SKILL.md）是 pi-coding-agent 层的机制，与 pi-durable 无关。
- **但扩展机制能力面足够**：
  - `Registry.install()` 支持运行时安装/原位替换，"publishes at once"；
  - `AgentState.extensions` 支持会话级选择（数组精确选定或 `{add, remove}` 增量编辑）；
  - `PromptSection.render` 可以是 async，prompt 构建期可读磁盘；
  - `wrapSection`/`wrapTool` 可包装既有内容。
- **Siftory 现状**：启动装 `[core, todo, CodingTools]` 后注册表静止；协议/HTTP 层未暴露扩展选择，会话级配置只有 model/thinking/instructions。
- **落地路径**：
  - Path A（推荐）：skill = markdown 工作法文件。写一个内建扩展，async section 在 prompt 构建时扫描 `workspace/skills/*.md` 拼入。Agent 用现有 write 工具写 md 即完成固化，host 侧写入前过审批。改动全在 Siftory。
  - Path B（暂不需要）：固化物升级成真工具时走运行时 `Registry.install()` + 会话级选择。涉及动态加载 Agent 所写代码，安全与打包需单独设计。
  - 零机制方案：固化的确定性脚本放 workspace 下由 bash 工具直接执行，无需注册。

## 八、不做清单

- 不做终端美学（monospace 时间线）——受众是内容创作者不是程序员
- 不做会话列表/历史浏览 UI
- 不做 Cmd-K 命令面板、看板视图、多主题市场
- 不在第 1 期动调色板和圆角体系
- 不做产物主视觉的手动指定（混合产物选错主角的问题真实出现再加）
- 不做完成时自动清理中间产物（见五·已知限制）
- 不预建 workspace 下的空目录
- 不做审批卡/人工确认门——Human in Control 暂由停止、对话纠偏、再创作实现（Q3 决策）；真实出现误用时再评估
- 不做显式完成标记——选题状态派生自 busy 信号（Q6 决策）
- 不做删除入口；首页已完成区只显示最新若干条，不做分页/完整档案（Q7 决策）
